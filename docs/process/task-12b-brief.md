# Task 12b: ASCII text encoding on the C64 and the first on-target run of the whole core

(Inserted between Task 12 and Task 13; not in the original plan. It resolves a design problem found in the Task 12 review and de-risks Tasks 14-16 by running the real compiler and VM on the C64 before the editor is built.)

## Why

- The language and all portable code are ASCII (source text, keywords, error messages, number formatting). Under `cl65 -t c64`, cc65/ca65 translate string and character literals to PETSCII by default, so keyword tables such as `"begin"` in lexer.c, error texts in errors.c, and `.byte "E"` in num_format would be PETSCII on the target, while source text in the editor/on disk is ASCII. Task 12's io layer currently accommodates both.
- Ruling (binding): ASCII is the internal text encoding everywhere in portable layers: the source buffer, lexer, compiler, VM, error texts, num_format/num_parse. PETSCII/screen codes exist only at hardware boundaries: keyboard in, screen out, disk files.
- The core (lexer, compiler, vm, turtle, clip, errors) has never been run on the C64. Its size, BSS use, speed and cc65 correctness are unknown. The editor must not be built before that is known.

## Part A: ASCII consistency

1. Make every portable and platform-layer object compile with an identity (ASCII) charmap on cc65 (the Task 12 tests already include `ascii_charmap.h`; find the cleanest mechanism, for example cc65's `--forced-include`/`#pragma charmap` or compiling with an identity target charmap, and apply it uniformly through the Makefile for all C sources that carry text literals: lexer, compiler, vm, errors, turtle, num_c64.c, io_c64.c, tests). In assembly sources use numeric byte values or an ASCII charmap so `'E'`, digits, `.`, `-` etc. are ASCII.
2. `num_format` must emit ASCII `E` (0x45); `num_parse` must accept ASCII `e`/`E` exactly like the host. Update tests/c64/num_check.c and its vectors accordingly (the 174 format vectors must still equal the host's output byte for byte, now with no PETSCII exception).
3. Remove the PETSCII accommodations in Task 12's io: the `$C1-$DA` branch in `io_scr` (io_c64.s ~984), `if (c == 0x65) c = 0x45;` in `io_read_num` (io_c64.c ~720), the `\xC5` expectations in tests/c64/io_check.c (feed10 and `charset()`). `io_put_str` takes ASCII and converts to screen codes at the screen boundary; `io_read_num` converts keyboard PETSCII to ASCII at the keyboard boundary (already so). Pick and document the charset in docs/architecture (upper/lower case charset: ASCII letters map to the matching screen codes).
4. Audit the portable core for assumptions that break with ASCII on a PETSCII-based cc65 runtime: any use of `<ctype.h>` (cc65's ctype tables follow the target charset: `isalpha('a'=0x61)` is false on c64!), `toupper/tolower`, `strcmp`-style helpers that are fine, `isdigit`. The lexer's case-insensitive identifiers/keywords must be implemented with explicit ASCII range checks (portable, tested on host and target). The grep in the Task 12 review also asked to check `-O` compiled core code for the cc65 2.18 miscompile `x = c == K ? K2 : c;` where operands are stack locals (see tests/c64/cc65_bug_ternary.c and docs/architecture/spike-results.md): grep the core and platform sources for `?:` on char/int locals and rewrite them as `if` statements where the pattern applies, noting each place.

## Part B: on-target end-to-end check of the core (core_check)

Create tests/c64/core_check.c and Makefile targets so that the REAL compiler and VM run on the C64 in VICE:

1. `make c64-core` builds `build/c64/core_check.prg` linking: lexer, compiler, vm, turtle, clip, errors (all of src/core), num_c64, gfx_c64, io_c64, with the proven link config. It embeds a handful of ASCII programs (as C string literals compiled with the ASCII charmap), runs each through `pl0_compile`/`pl0_run`, and prints results on screen; the harness checks the screen lines (whole-line match). Programs: (a) `!1+2*3.` (prints 7); (b) factorial of 10 with a recursive procedure with a parameter (3628800); (c) the error `!x.` -> `ERROR line 1: undeclared name` (use the same message text builder as the final UI will: `ERROR line N: <err_text>`); (d) runtime error division by zero with the right line; (e) `sin`/`sqrt`/`atan` values printed (`4*atan(1)` -> 3.14159265); (f) recursion depth 40 sum -> 820 and the runaway recursion case -> `stack overflow (too deep)` without damage (the machine is still usable afterwards: run another program); (g) a STOP test: `var i; begin i := 0; while 1 = 1 do i := i + 1 end.` must end with `ERROR line 1: stopped` after the harness injects the RUN/STOP key (monitor `keybuf` or matrix forcing as Task 12 did); (h) a drawing (a square via forward/turn) whose bitmap is checked with tools/check_bitmap.py against the host renderer's pixel count (the existing Task 12 mechanism).
2. `make c64-example EX=<name>` builds core_check with ONE of the 15 examples in examples/ embedded (converted from the .pl0 file at build time to a C array with a small tool, ASCII bytes verbatim) and runs it in VICE; for text examples it compares the screen/output text with `examples/<name>.expected` using the tolerant comparison of tools/compare_output.py (output longer than the screen: have the harness capture the output through a RAM buffer that the checker dumps via the monitor, or print to screen and scroll-check only the tail; choose what is reliable and say so); for drawings it compares the bitmap pixel count with the host render of `examples/<name>.lines` within 3% (5-byte floats move pixels by a pixel or two) and requires the same bounding box within 2 pixels. `make c64-examples` runs all 15 sequentially and prints a table: example, result, emulated seconds (measure the real C64 run time in emulated CPU cycles: for example start/stop cycle counters through the VICE monitor or a CIA timer read before and after pl0_run, not wall-clock; remember TI loses ticks during gfx_line (see docs), so prefer CIA timer 1/2 cascaded or a cycle count from the monitor) and P-code count if cheaply available. Record the table in docs/architecture/examples-budget.md (add a C64 time column) — the spec requires every example to finish in about 30 s or less at normal speed.
3. Memory report (docs/architecture/spike-results.md or a new docs/architecture/memory-map.md): per-module sizes from the linker map (code, data, BSS), total image, BSS end versus the `$97FF` limit, bytes free, where the 8192-byte source buffer (BASICBSS at $A000) and the static `Program` live. If the core does not fit: STOP and report BLOCKED with the numbers and the options (for example reduce MAX_CODE, move the VM loop to assembly, trim error texts), do not weaken limits silently.
4. If an example is too slow (> 30 s) or wrong on the target, investigate: tune the example (parameters) if that is the fix, or report BLOCKED/NEEDS_CONTEXT if the interpreter is at fault. Do not change the language semantics.

## Constraints

- `make test` (host) stays pure host and pristine; every existing on-target target (`c64-num`, `c64-gfx`, `c64-io`) stays green; host tests of the lexer must still pass after the ASCII audit (add host tests for any new classification helper).
- C89-style declarations at block start, no heap, no cc65 warnings, no build artifacts committed, all ROM/banking/zero-page rules from the spike. The source buffer is the ONLY thing allowed in $A000-$BFFF and never passed to fp_* shims.
- Document the new targets and the encoding decision in docs/architecture/testing.md.
- Small commits (encoding; core_check; examples harness; docs).
