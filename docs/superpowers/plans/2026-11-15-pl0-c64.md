# PL/0 Turtle for the Commodore 64 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A PL/0 interpreter (with floats, procedure parameters and turtle graphics) that runs on a C64 with a function-key editor, ships with math examples, and is playable in a browser from GitHub Pages.

**Architecture:** One portable C core (lexer → compiler emitting P-code → stack VM) written against three thin platform interfaces: numbers (`num.h`), graphics (`gfx.h`) and I/O (`io.h`). Each has a host implementation (Linux, used by all automated tests) and a C64 implementation (cc65 C plus assembly shims calling the BASIC ROM float routines and a bitmap line routine). The C64 front end (editor, example picker, run screen, disk save/load) sits on top and is verified by a scripted VICE smoke test.

**Tech Stack:** C99 for host (gcc), cc65 (`cl65`, `ca65`) for C64, GNU make, Python 3 (build tools and test comparison only), VICE (`x64sc`, `c1541`) for on-target tests, a vendored JavaScript C64 emulator for the web demo, GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-11-15-pl0-c64-design.md`

## Global Constraints

- Target is a stock C64, about 38 KB free RAM shared by editor, source, compiled code, VM and stack.
- BASIC ROM must stay visible (floating point uses its routines); nothing may be placed at `$A000–$BFFF`.
- Source text must survive a run and a drawing; the user returns to the editor with the program intact.
- No color and no sound commands in the language. UI uses the default C64 palette.
- Graphics: 320×200 monochrome bitmap, black on white.
- Function keys: F1 Run, F3 Open (example list), F5 Save, F7 Help. ESC stops a running program.
- Errors show as `ERROR line N: <plain message>` on the bottom line with the cursor on that line.
- Every built-in example must load, compile and finish in under about 30 s at normal C64 speed.
- Examples are authored as plain ASCII `.pl0` files and converted at build time; saved programs are plain text.
- Compiler and VM must compile unchanged for both host and C64; only `num`, `gfx`, `io` differ.
- Web demo: static files only, emulator vendored in the repo, license must permit redistribution; if no emulator qualifies, stop and ask the author.
- Commits are small, one per task step group, with meaningful messages.

## Language Definition (decisions this plan makes where the spec leaves a choice)

- One numeric type: C64 float. Literals: `12`, `3.14`, `0.5`. Unary minus allowed.
- `const n = 5;` `var a, b;` `procedure p(x, y); … ;` `call p(1, 2)` (parameters by value, the `(…)` part optional when there are none). `begin … end`, `if c then s`, `while c do s`, no `else`. Conditions: `odd e`, `= # <> < <= > >=`.
- Output: `!expr` or `!'text'`. Input: `?var`. `!expr` and `!'text'` print without a trailing newline; a bare `!` prints a newline.
- Comments: `{ … }`.
- Math functions in expressions: `sin cos atan sqrt abs int exp log` (radians; `int` is floor).
- Turtle statements: `forward(e)`, `turn(e)` (degrees, positive = clockwise), `penup`, `pendown`, `home`, `moveto(x, y)` (draws if pen down). Coordinates: origin at screen center, x right, y up, range x −160…159, y −100…99. Start state: at origin, heading up, pen down. Drawing outside the screen is clipped.
- Keywords and identifiers are case-insensitive; identifiers up to 16 chars.

## Review Focus

Failure modes the spec implies but no feature task would exercise by itself. Each has a test inside the owning task.

1. Division by zero, `sqrt` of a negative, `log` of ≤ 0 → runtime error with line, no crash (Task 8).
2. Runaway recursion → plain "stack overflow" error, no memory corruption (Task 7).
3. Empty program, comment-only program, missing final `.`, `0.1 + 0.2` printing as `0.3`, huge and tiny numbers (Tasks 2, 5).
4. Turtle far off-screen or with huge distances → clipped, never wraps or writes outside the bitmap (Task 9).
5. Source buffer full, empty file name or bad characters on save, and an infinite loop stopped by ESC (Tasks 13, 15, 12).

## Amendments after the Task 1 spike (2026-11-15)

Binding on later tasks; source: `docs/architecture/spike-results.md`.

- **Limits (Task 4):** `MAX_CODE 768`, `MAX_IDENTS 64`, `MAX_STACK 512`, `MAX_NEST 4`, `MAX_SOURCE 8192`, `MAX_CONSTS 128`, `MAX_STRINGS 1024`. The draft values did not fit.
- **Source buffer under BASIC ROM:** the source text lives in RAM at `$A000–$BFFF`. The `fp_*` shims bank the ROM in only during a call and normal code runs with `$01 = $36`. Never pass pointers into that area to `fp_*`. Task 15 must test disk SAVE/LOAD with the buffer there; if that fails, `MAX_SOURCE` drops to 4096.
- **Link config and memory map:** use `spikes/rom-float/pl0-c64.cfg` as the starting point, bitmap at `$E000`, screen matrix at `$CC00` (VIC bank 3). Keep BSS end ≤ `$97FF` and check the linker map in every C64 task.
- **Examples are loaded from the disk image,** not embedded in a C array. `tools/embed_examples.py` (Task 15) becomes a disk-image builder; the web demo autostarts the `.d64`.
- **Speed:** ROM `sin` ≈ 28 ms. The turtle (Task 9) caches sin/cos of the heading and recomputes only when the heading changes. The example instruction budget in Task 10 is about 40,000, not 2,000,000.
- **Task 12:** read section 9 of the spike results first; it records a cc65 `conio` scrolling hazard and the notes for the `fp_*` shims.
