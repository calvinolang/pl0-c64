# PL/0 Turtle for the Commodore 64 — Design

Date: 2026-11-15 · Status: draft for approval

## 1. Intent and why

Build a PL/0 interpreter that runs on a Commodore 64 (tested in VICE), extended with floating-point numbers and turtle graphics. A user types or loads a PL/0 program, presses a key, and sees numbers or a drawing.

The project has a second purpose: it is a **showcase of the Superpowers workflow** (brainstorm → design → plan → build) and a way for its author to become fluent with it. The author likes retrocomputing and Pascal, which is why the topic is Wirth's PL/0. The outcome must be impressive to colleagues, so documentation, user experience and the visible development trail are part of the deliverable, not extras.

### The colleague scenario (the success test)
A colleague will:
1. Open the GitHub repository and find professional documentation.
2. Run the software themselves, ideally in a JavaScript C64 emulator embedded in a GitHub Pages site, and be surprised by the quality of the user experience given the retro constraints.
3. Read the main README and understand how Superpowers was used.

Success: from the Pages link, within about a minute, the colleague picks an example, sees a drawing appear, edits a number and re-runs it.

## 2. Goals, non-goals, anti-goals

**Goals**
- Edit, run and save PL/0 programs on a C64 with an easy, discoverable interface.
- Math-oriented built-in examples: numerical computation and graphical drawings.
- Floating-point arithmetic and turtle graphics, with the language otherwise as small as PL/0.
- A web-playable demo plus downloadable `.prg` and `.d64` for VICE.
- Professional documentation and a visible development trail.

**Non-goals**
- Color and sound (the UI uses the default C64 palette; programs have no color or sound commands).
- Language features that don't serve the math and drawing examples (records, strings as a type, file I/O from programs, etc.).
- Speed beyond "a drawing completes in a reasonable time".

**Anti-goals** (failure even if it technically works)
- It feels like a toy or a 1982 tool with cryptic behavior.
- Error messages that need decoding.
- A demo that only works in desktop VICE, or only after setup steps.
- Documentation that describes the project but doesn't show how it was built.

## 3. Constraints

- Target: stock C64, about 38 KB of free RAM for editor, source text, compiled code, interpreter and stack. Memory is the main technical risk.
- Toolchain: cc65 (C and assembly) producing a `.prg`.
- Floating point uses the C64 BASIC ROM routines (5-byte format), called through small assembly shims.
- Graphics: the 320×200 monochrome bitmap mode; the editor uses the text screen.
- The web demo must run from GitHub Pages (static files only).

## 4. Approaches considered

**Implementation approach**

- **A. cc65 C, compiling to P-code (chosen).** Editor, compiler and VM in C; the compiler emits P-code (the stack-machine code of Wirth's own PL/0 compiler); the VM runs it. Small assembly routines for ROM floating point and bitmap drawing. Fastest to build, readable, mostly testable natively on Linux. Costs: bulkier code than assembly (less room for programs) and slower execution; the VM's inner loop can move to assembly later if needed.
- **B. Pure 6502 assembly.** Smallest and fastest, but several times the effort, hard to test, and unreadable for colleagues. Rejected.
- **C. cc65 C walking the program text directly, no P-code.** Simpler at first, but slow (re-reads text on every loop) and loses the link to Wirth's design. Rejected.

**User interface**

- **A. Editor first, function keys (chosen), with an example list reachable from it (F3).**
- **B. Start menu, then editor.** Rejected: an extra screen on every visit.

## 5. The language

Base: Wirth's PL/0 — `const`, `var`, `procedure`, `call`, `begin … end`, `if … then`, `while … do`, `odd`, and `!` (output) / `?` (input). Extensions below are decided unless marked *(builder's call)*.

- **Numbers:** floating point (decided). Whether integers and floats are separate types or everything is one float type is *the builder's call*; the author's preference is the simplest option, which is a single float type.
- **Procedure parameters (decided):** `procedure koch(len, depth)` and `call koch(10, 3)`. Pass by value. Recursion must work.
- **Turtle graphics (decided):** statements for moving forward, turning (degrees), pen up/down, and returning home. The exact set and names are *the builder's call*, with the following needed by the examples: forward, turn, pen up, pen down, home (center, facing up), and moving to an absolute point (for plotting functions).
- **Math functions (decided in principle):** the ROM-supported set the examples need, such as sin, cos, atan, sqrt, abs, int, exp, log. Trig functions use radians; the turtle turns in degrees. *(my call, chosen to match the ROM and normal math usage)*
- **Output:** `!` prints a number; it also accepts a string literal so programs can label results (`! 'pi = '`). *(my call)*
- Keywords are case-insensitive. How source is stored given the C64 character sets is the builder's call.

## 6. User experience

Four screens on the 40×25 text screen plus the bitmap screen (mockups were reviewed and approved in the brainstorming session):

1. **Editor.** Status line on top (program name, line, column), function-key bar at the bottom: F1 Run, F3 Open, F5 Save, F7 Help. Starts with a short example loaded, so the first keypress can be F1.
2. **Example picker (F3).** A list of examples, each with a one-line description. User-saved programs appear in the same list. RETURN opens, ESC goes back.
3. **Run.** Text output from `!` appears on a text screen; the first turtle command switches to the full-screen bitmap. When the program ends (or on a key), the user can toggle between text and drawing and return to the editor. ESC stops a running program. *(the toggle/return key details are my call)*
4. **Errors.** Syntax and runtime errors return to the editor with the cursor on the offending line and a plain-language message in the bottom line, e.g. `ERROR line 6: ";" expected`. Runtime errors include division by zero and stack overflow, with equally plain messages.

Editing basics: cursor movement, insert and delete, home/end, and a way to start a new program. Anything beyond that needs a reason tied to ease of use.

Examples are **embedded in the program image**, so the web demo works without a disk. Saving to disk (device 8) is supported; persistence in the web emulator is best-effort and must be documented honestly.

## 7. Examples (math oriented)

Numerical computation and drawings, roughly: factorial (procedure with parameter, recursion), primes, Newton's square root, π from a series, GCD; drawings: square, spiral, regular polygon, Koch snowflake, fractal tree, plot of sin(x), Lissajous curve. The final list and wording are the builder's call, but it needs both categories and at least one example that uses recursion with parameters and one that uses floating point visibly.

## 8. Quality, testing and delivery

- **Shared core:** compiler and VM are written so they also compile natively on Linux, with the float and graphics layer swapped for host versions. This allows automated tests of every example without an emulator. Host doubles and C64 5-byte floats differ slightly, so expected outputs are compared with a tolerance.
- **On-target check:** at least a smoke test that the real `.prg` boots in VICE and runs an example, if headless VICE is available. This must be reproducible, not manual.
- **Early spike:** before the full build, a throwaway check of memory budget (how large the code is and how much is left for programs) and of ROM-float calls from cc65. The memory result decides whether the VM loop moves to assembly.
- **Delivery:** `.prg` and `.d64` built by a single documented command; GitHub Pages site embedding a JavaScript C64 emulator that autostarts the program. Which emulator is the builder's call, subject to its license allowing redistribution and its ability to run the bitmap mode and autostart.

## 9. Documentation and development trail

- README: what it is, a screenshot or GIF, a link to the live demo, quick start, and a "How this was built with Superpowers" section.
- User guide (editing, running, saving, the examples) and language reference (every statement, function and error message).
- Short architecture write-up (compiler, P-code, VM, memory map, float/graphics layer).
- The design documents and plans live in `docs/superpowers/` and are linked from the README; git history is kept meaningful (the repository was initialized as part of this design step).

## 10. Left to the builder

Memory map and module layout; P-code instruction set; number representation details; exact turtle and math function names and signatures; editor internals (text buffer, gap buffer or similar); disk format and file naming; choice of web emulator; project structure and test tooling; the example list.

## 10b. Designer's calls after builder review

These settle questions a reviewer raised; they are my proposals and open to change.

1. **Program size.** The example programs define the minimum: every built-in example must load, compile and run. If the spike shows they don't fit, the first response is to move the VM to assembly or bank RAM under the ROMs, not to drop examples.
2. **Memory and screens.** The BASIC ROM must stay visible for floating point, so the bitmap and program image are placed in RAM outside `$A000–$BFFF`. The source text must survive a run (the user returns to the editor after drawing and re-runs). The text screen need not survive; it is redrawn on return.
3. **On-target test.** Where VICE is available, the smoke test is a required gate for milestones; otherwise it is documented as a manual step. The setup is described in the README so it can be reproduced.
4. **Web demo licensing.** Use only an emulator whose license allows hosting it on GitHub Pages, and whose ROM situation (the demo needs a working BASIC ROM for floats) is legally publishable. Vendor it into the repository so the demo works from static files. If no emulator meets this, stop and ask the author, because it affects whether the demo can be published.
5. **Run time.** Each built-in example should finish in under about 30 seconds at normal C64 speed; the web demo may offer a warp (fast-forward) option. Examples are tuned to meet this, for instance with a lower recursion depth for the snowflake.
6. **Character set.** Examples are authored on the host as plain ASCII text; the build converts them. Saved programs must be plain text that converts losslessly, so users can read them on a PC.
7. **Error messages.** Designed as the parser is written, kept in one table, and the language reference's error list is generated from or checked against that table. Each message is covered by a test.

## 11. Risks

- **Memory** (38 KB shared by everything) — mitigated by the early spike and by the option to move hot code to assembly.
- **Web emulator limits** (bitmap support, autostart, disk persistence) — verify early.
- **Float differences between host and C64** — tolerance in tests, a thin float abstraction layer.
